Deploying `as-control-plane` on a server with a public or intranet HTTPS endpoint lets you access your workspace from any browser or macOS client and enroll developer machines across networks with a single command.

Database migrations are embedded inside the Go binary — **your production server does not need Go, Node.js, pnpm, or repository source code**, only the compiled release artifacts plus Control Plane infrastructure (PostgreSQL, NATS JetStream, and Redis).

## Step 1: Build Control Plane & Cross-Platform Node Bundles

On a build machine, run the release packaging script to produce both the Control Plane binary and multi-platform node archives in one step:

```bash
node scripts/build-host-binaries.ts
```

This produces two sets of artifacts:

1. **`as-control-plane`**: Static Go binary (`CGO_ENABLED=0`) deployed on the Control Plane server.
2. **Node distribution directory (mounted via `-node-dist-dir`)**: Contains `<os>-<arch>.tar.gz` archives and matching `.sha256` checksum files for `darwin-arm64`, `linux-amd64`, and `linux-arm64` (packaging `as-workspace-server`, standalone `as-adapter-host`, and the `as-delegate` launcher). The Control Plane serves version-matched archives directly at `GET /downloads/node/<os>-<arch>.tar.gz`.

<Aside type="note" title="Partial Platform Bundles">
If `-node-dist-dir` is omitted or missing a specific platform archive, `as-control-plane` still boots normally and surfaces missing targets (`unavailable_platforms`) in the Web UI's "Add Host" dialog.
</Aside>

## Step 2: Configure HTTPS & Network Listeners

`as-control-plane` serves the Web UI, Connect RPC API, `/install.sh`, `/downloads/`, and the node gateway (`/v1/node/*`) over a single external HTTPS origin.

<Aside type="danger" title="TLS & Proxy Requirements">
1. **Use a certificate issued by a publicly trusted CA** (such as Let's Encrypt, `tailscale cert`, or a commercial CA): execution nodes validate TLS strictly against the OS root trust store and reject self-signed or private CAs.
2. **Never place behind a TLS-decrypting third-party CDN/proxy**: outer TLS is the sole encryption layer protecting Route Credentials and source-code streams. Terminate TLS directly on `as-control-plane` or on a reverse proxy you fully control.
3. **Never enable no-login mode in production**: keep `-local-no-login=false` (the default) and never expose a loopback debug instance via port forwarding.
</Aside>

Choose whichever topology matches your server setup:

<Tabs>
  <TabItem label="Option A: Direct TLS Termination">
    Ideal for single-server deployments without Nginx or Caddy. Pass database, NATS, and Redis credentials via environment variables so secrets do not appear in process argument lists:

    ```bash
    export AS_CONTROL_PLANE_PG_URL="postgres://user:pass@127.0.0.1:5432/seedrail?sslmode=disable"
    export AS_CONTROL_PLANE_NATS_URL="nats://user:pass@127.0.0.1:4222"
    export AS_CONTROL_PLANE_REDIS_URL="redis://:pass@127.0.0.1:6379/0"
    export AS_CONTROL_PLANE_ATTACHMENT_DIR="/var/lib/seedrail/attachments"

    ./as-control-plane \
      -listen 0.0.0.0:443 \
      -base-url https://cp.example.com \
      -tls-cert-file /etc/letsencrypt/live/cp.example.com/fullchain.pem \
      -tls-key-file /etc/letsencrypt/live/cp.example.com/privkey.pem \
      -node-dist-dir /opt/seedrail/node-dist
    ```
  </TabItem>
  <TabItem label="Option B: Behind Your Own Reverse Proxy">
    If Caddy or Nginx already manages port 443 on your server, bind `as-control-plane` to loopback or a private interface and declare your proxy subnet in `-trusted-proxy-cidrs` so rate limits key off real client IPs:

    ```bash
    export AS_CONTROL_PLANE_PG_URL="postgres://user:pass@127.0.0.1:5432/seedrail?sslmode=disable"
    export AS_CONTROL_PLANE_NATS_URL="nats://user:pass@127.0.0.1:4222"
    export AS_CONTROL_PLANE_REDIS_URL="redis://:pass@127.0.0.1:6379/0"
    export AS_CONTROL_PLANE_ATTACHMENT_DIR="/var/lib/seedrail/attachments"

    ./as-control-plane \
      -listen 127.0.0.1:8080 \
      -base-url https://cp.example.com \
      -trusted-proxy-cidrs 127.0.0.1/32,::1/128 \
      -node-dist-dir /opt/seedrail/node-dist
    ```

    Ensure your reverse proxy satisfies three forwarding rules:
    - Enables **WebSocket Upgrade** (covering `/connection/websocket` and `/v1/node/*`);
    - Passes the `Authorization` header through unmodified;
    - Sets `X-Forwarded-For` accurately.
  </TabItem>
</Tabs>

## Configuration Reference

Every option accepts either a CLI flag or its matching environment variable (CLI flags take precedence):

| CLI Flag | Environment Variable | Default | Description |
| --- | --- | --- | --- |
| `-listen` | `AS_CONTROL_PLANE_LISTEN` | `127.0.0.1:8080` | HTTP/HTTPS listen address |
| `-base-url` | `AS_CONTROL_PLANE_BASE_URL` | Listen address | Canonical public HTTPS origin used when minting login URLs and `install.sh` (ignores request `Host` headers) |
| `-pg` | `AS_CONTROL_PLANE_PG_URL` | Local dev DSN | PostgreSQL connection string (runs embedded migrations on startup; pass via env var in production) |
| `-nats` | `AS_CONTROL_PLANE_NATS_URL` | `nats://127.0.0.1:14222` | NATS (with JetStream) URL; supports account credentials in URL userinfo |
| `-redis-url` | `AS_CONTROL_PLANE_REDIS_URL` | Empty | Redis URL storing 1-hour node enrollment tokens only; if unset or unreachable, only new/re-enrollment is paused while existing online hosts stay unaffected |
| `-env-name` | `AS_CONTROL_PLANE_ENV_NAME` | `prod` | Environment name used as the Redis token key prefix (`<env>:`) |
| `-node-dist-dir` | `AS_CONTROL_PLANE_NODE_DIST_DIR` | Empty | Directory containing `<os>-<arch>.tar.gz` and `.sha256` node bundles |
| `-tls-cert-file` / `-tls-key-file` | `AS_CONTROL_PLANE_TLS_CERT_FILE` / `AS_CONTROL_PLANE_TLS_KEY_FILE` | Empty | PEM certificate chain and private key paths when terminating TLS directly |
| `-trusted-proxy-cidrs` | `AS_CONTROL_PLANE_TRUSTED_PROXY_CIDRS` | Empty | Comma-separated list of trusted reverse-proxy CIDRs |
| `-attachment-dir` | `AS_CONTROL_PLANE_ATTACHMENT_DIR` | `~/.local/state/agent-system/attachments` | Directory storing message attachment blobs |
| *(env var only)* | `AS_CONTROL_PLANE_DELEGATION_KEY` | Sibling `delegation.key` file | HMAC secret for delegation tokens (≥16 chars; auto-generates a `0600` key file on first boot and must persist across restarts) |
| `-session-ttl` | `AS_CONTROL_PLANE_SESSION_TTL` | `720h` | Idle session expiration window (sliding renewal while active) |

## Step 3: First Admin Login & Backups

<Steps>

1. **Verify health probe**

   ```bash
   curl -f https://cp.example.com/healthz
   ```

2. **Mint your initial login link**

   Run the built-in `token generate` subcommand on the Control Plane server to issue a single-use login URL (valid for 10 minutes by default):

   ```bash
   ./as-control-plane token generate -base-url https://cp.example.com
   ```

   Open the printed `https://cp.example.com/login?token=...` URL in your browser to sign in.

3. **Schedule paired backups**

   `as-control-plane` runs as a single writer with compact durable state:
   - **Back up together**: PostgreSQL database + `-attachment-dir` (along with the sibling `delegation.key`). Because host identity digests live in PostgreSQL, restoring from backup allows every enrolled host to reconnect automatically using its existing local Route Credential without re-running `install.sh`.
   - **No backup required**: Redis (ephemeral enrollment tokens) and NATS JetStream (transient streaming buffer).

</Steps>

Once your Control Plane is live, continue to [Add Execution Hosts](/deployment/add-host/) to enroll laptops and remote servers.
